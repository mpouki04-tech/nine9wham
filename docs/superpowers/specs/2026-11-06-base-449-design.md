# Base 449 reconstruite + purge etendue du compte fantome (w11)

Date : 2026-11-06
Statut : approuve (2026-11-06)

## Pourquoi

L'IPA RyukGram **449.0.0** de l'utilisateur fonctionne sur son appareil
(c'est elle qui cree les comptes sans planter). Notre build actuel est
construit sur une base **454.0.0** nettoyee, avec notre `Peter.dylib`
injecte par un seul `LC_LOAD_WEAK_DYLIB`. La seule variable jamais testee
est donc la **base 449** et l'**infrastructure d'injection a 4 slots** de
l'IPA qui fonctionne.

Deux symptomes persistent sur notre build 454 :

1. **Crash a la saisie du prenom** a la creation de compte -> retour a
   l'accueil. Cause racine documentee en w10-2 (keystore App Attest
   `group.com.facebook.family.appattestation`, attestation bloquee), mais
   le bloc `CRASH` du Report n'a jamais ete fourni ; aucune preuve n'exclut
   la base 454 ni l'injection.
2. **Compte fantome `61516395224`** : la purge w10-7 a bien supprime les
   items marques `_ryg_` (54 items restants, 0 legacy), mais la forensique
   post-purge montre que le fantome survit dans des **items natifs
   Instagram sans marqueur** : `device_based_login.growth`
   (`61516395224-kIGOneTapLoginLastLogoutTimestamp`),
   `persistent_accounts.growth` (+ `last_logged_in_user_pk`).

L'utilisateur demande explicitement : decomposer tous les fichiers de
l'IPA 449, effacer toutes les traces RyukGram, implanter notre code **de
la meme facon et avec la meme infrastructure qu'eux**, et remplacer
l'IPA de base par ces nouveaux extraits.

## Objectifs

1. Reconstruire une base **449.0.0** a partir de l'app extraite de l'IPA
   RyukGram qui fonctionne, en supprimant **tous** ses artefacts et en
   reecrivant ses **4** commandes de chargement en place.
2. Injecter `Peter.dylib` dans exactement les memes slots (1 Peter +
   3 slots faibles inertes), sans faire grossir le binaire, avec le meme
   `LC_RPATH @executable_path/Frameworks`.
3. Etendre la purge du keychain aux **stores natifs du fantome** (sans
   marqueur RyukGram), avec preuve dans le Report, sans toucher au vault
   ni aux items non prouves.
4. Remplacer l'asset de la release `base` et publier
   `nine9wham_instagram_449.ipa`.
5. Verifier sur appareil : fantome absent, creation de compte (prenom)
   testee ; si le crash persiste, le bloc `CRASH` du Report devient
   obligatoire (aucun fix devine).

## Non-objectifs

- Corriger le crash prenom **sans preuve** : le changement de base est
  l'experience demandee, pas un diagnostic definitif.
- Conserver un seul fichier ou une seule fonction de RyukGram
  (`RyukGram.dylib`, `FLEXing`, `libflex`, `NoPluginsPatch`,
  `CydiaSubstrate`, `RyukGram.bundle`, `_CodeSignature`).
- Supprimer `PhantomSideloadFix` (Sideloadly, pas RyukGram) ni
  `ai.fylio.app / identity` (autre app) ni le vault `nine9wham`.
- Modifier le comportement d'attestation (w10-2, inchange) ou le flux
  d'inscription Instagram.
- Reconstruire les extensions absentes de l'IPA 449 (`Extensions/` et
  `PlugIns/` sont vides dans l'IPA qui fonctionne) : on preserve la base
  telle qu'elle fonctionne.

## Approches considerees

1. **Retenue — A (validee par l'utilisateur) : base 449 + notre dylib
   dans leur infrastructure + purge etendue.** On reproduit la seule
   configuration prouvee fonctionnelle chez l'utilisateur (base 449,
   4 slots, meme rpath) en remplacant leur code par le notre, et on
   ajoute la purge des stores natifs du fantome.
2. **Ecartee — B : rester en 454 et ne faire que la purge.** Ne teste
   pas la base, alors que c'est la demande et la seule variable jamais
   essayee ; le crash prenom reste sans explication.
3. **Ecartee — C : base 449 + garder `NoPluginsPatch`/`RyukGram.dylib`.**
   Violerait l'exigence 0 trace et melangerait deux tweaks (conflits de
   hooks keychain/attestation deja constates).
4. **Ecartee — D : 4 copies de `Peter.dylib`.** Chargements dupliques
   inutiles et risque de double constructeur ; les slots 2-4 doivent
   rester des faibles **absents** (`@rpath/NWSupport.dylib`), motif deja
   utilise en w10-2.

## Comment (decisions)

### 1. Reconstruction de la base 449

Nouveau script `scripts/prepare_base.py` (outil de build, pas une
dependance du tweak) :

- source : `_triage_ryuk/extracted/Payload/Instagram.app` (l'app exacte
  de l'IPA 449 qui fonctionne) ;
- copie dans un dossier temporaire, puis suppression recursive de
  `Frameworks/RyukGram.dylib`, `Frameworks/FLEXing.dylib`,
  `Frameworks/libflex.dylib`, `Frameworks/NoPluginsPatch.dylib`,
  `Frameworks/CydiaSubstrate.framework`, `RyukGram.bundle`, et de tout
  dossier `_CodeSignature` ;
- reecriture **en place** des 4 `LC_LOAD_WEAK_DYLIB` :
  idx 164 -> `@rpath/Peter.dylib`, idx 165-167 ->
  `@rpath/NWSupport.dylib` ; `cmdsize`, `ncmds` et `sizeofcmds` ne
  changent pas ; le reste de chaque commande est zero ;
- `cyan.entitlements` conserve (parite avec l'IPA qui fonctionne) ;
  `Extensions/` et `PlugIns/` vides ne sont pas ajoutes au zip ;
- zip deterministe `Payload/Instagram.app/...`, modes Unix explicites
  (`100755` pour les Mach-O, `100644` sinon), pas de `__MACOSX` ;
- le script **verifie** ensuite l'IPA produite : hash binaire
  `b3f98e67…`, 2079 fichiers, 1 Peter + 3 NWSupport, 0 marqueur, 0
  artefact, `Peter.dylib` absent, `_CodeSignature` absent.

La base est produite **une seule fois** en local (l'IPA 449 d'origine
n'est plus sur le disque) puis **publiee comme asset** de la release
`base` : `com.burbn.instagram_v449.0.0_sideload_clean.ipa`. A partir de
la, la CI est **reproductible depuis cet asset** (telechargement +
verification du hash) ; `prepare_base.py` reste dans le depot pour
l'audit et la re-generation depuis l'app extraite, mais n'est pas
executee par la CI.

### 2. Infrastructure d'injection

- Le binaire de base reference **deja** `@rpath/Peter.dylib` en faible :
  `inject_dylib.py` devient un no-op explicite (il imprime « Deja lie »).
- Le CI copie `build/Peter.dylib` dans `Frameworks/Peter.dylib` et le
  signe ad-hoc, comme avant.
- Les 3 slots `@rpath/NWSupport.dylib` restent **faibles et absents** :
  dyld les ignore, exactement comme dans l'IPA de reference w10-2.
- Aucun nouveau `LC_LOAD_DYLIB` fort, aucune croissance du binaire.

### 3. Purge etendue du compte fantome

Nouvelle brique dans `Peter.m`, a cote de la purge w10-7 :

- **`NWGhostPK()`** : chaine decimale construite par **arithmetique**
  (`61516 * 1000000 + 395224`), jamais un litteral ASCII. Le binaire ne
  contient donc jamais `61516395224`.
- **`NWKeychainPurgeGhost(trigger)`** : enumere les memes 2 classes
  (`kSecClassGenericPassword`, `kSecClassInternetPassword`) que la
  purge legacy. Le test de famille porte sur **le service ET
  l'account** (insensible a la casse) :
  - `device_based_login.growth`
  - `cloud_based_login.growth`
  - `persistent_accounts.growth`
  - `com.instagram.users.persistent_accounts`
  - `com.instagram.users.last_logged_in_user_pk`
  - `last_logged_in_user_pk`
- **Condition de suppression** (jamais la famille seule) :
  - l'`account` contient le pk, **ou** le `kSecValueData` contient le
    pk en ASCII **ou** en entier 8 octets big-endian / little-endian ;
  - **ou** `device_based_login.growth` avec un `account` prefixe
    `<pk>-` (cas `61516395224-kIGOneTapLoginLastLogoutTimestamp`) ;
  - **ou** `account` = `zxPluginsInjectGenericEntry` (reste du shim
    zxPlugins de RyukGram), chaine construite par concatenation
    (`@"zx"` + `@"PluginsInjectGenericEntry"`) pour ne jamais ecrire
    `zxPlugins` en clair.
- **Cas couverts par les tests** : (a) service
  `device_based_login.growth`, account `<pk>-kIG...` ; (b)
  `persistent_accounts.growth`, account neutre, data contenant le pk ;
  (c) `com.instagram.users.last_logged_in_user_pk`, account neutre,
  data = pk ; (d) account `last_logged_in_user_pk`, service vide, data
  pk ; (e) meme famille mais data/account d'un autre compte -> **jamais
  supprime**.
- **Item partage (plusieurs comptes)** : si un item contient le pk
  **et** d'autres comptes, on supprime **l'item entier** (pas de
  reecriture d'un blob plist/NSKeyedArchiver opaque). Consequence
  assumee : le « one-tap » des autres comptes peut etre perdu ; leurs
  sessions actives (cookies/prefs des conteneurs) ne sont pas touchees.
  Meme regle pour les cles de prefs : la cle entiere est retiree si sa
  valeur contient le pk.
- **Garde-fous** : jamais notre vault (`nine9wham`), jamais un item
  seulement « candidat » dont la data est illisible et dont l'account ne
  contient pas le pk (log `UNREADABLE`, on ne supprime pas), requete de
  suppression stricte (classe + service/account/accessGroup enumeres).
- **`NWPrefsPurgeGhost(trigger)`** (defense en profondeur) : dans le
  domaine bundle et dans chaque suite `nw9.*`, retire les cles
  `com.instagram.users.persistent_accounts`,
  `com.instagram.users.last_logged_in_user_pk` et toute cle contenant
  `last_logged_in_user_pk`, **uniquement** si la valeur contient le pk.
- **Declencheurs** : les 3 memes qu'en w10-7 — boot 12 s (avant la
  forensique, flag `nw9_kcpurge_done` = `NWBuildID`), Reset (avant
  `exit(0)`), bouton Device identity. Chaque suppression est loguee
  `[NW] kc-ghost: [trigger] deleted service=… account=…` et synthetisee
  `legacy=L ghost=G`.
- **Politique du flag `nw9_kcpurge_done`** : il n'est ecrit **que si**
  l'enumeration des 2 classes est complete et qu'aucun item cible n'est
  reste `UNREADABLE`, et qu'aucun `SecItemDelete` n'a echoue. Sinon le
  flag **n'est pas ecrit** : la purge retente au boot suivant (pas de
  boucle bloquante ; au pire un retry par lancement, log
  `INCOMPLETE`). La forensique reste correcte puisqu'elle lit l'etat
  reel apres la tentative.
- **Items laisses volontairement** : `PhantomSideloadFix` (Sideloadly),
  `ai.fylio.app / identity` (autre app). Ils ne sont pas RyukGram.

### 4. Forensique et UI

- La ligne keychain devient
  `keychain N items (L legacy, G ghost)` ; chaque item est marque
  `LEGACY` ou `GHOST` dans le Report ; l'alerte ajoute
  `GHOST ITEMS PRESENT: G` tant qu'il en reste.
- L'en-tete `SESSION FORENSICS w10-5` devient dynamique
  (`SESSION FORENSICS <NWBuildID>`) : correction du libelle fige.
- Le flag `nw9_forensics_done` passe de « simple existence » a
  **build-keyed** : il contient `NWBuildID` et n'est valide que si la
  valeur correspond au build courant. Une mise a jour d'IPA rejoue donc
  automatiquement la forensique w11 (sans dependre du Reset).
- Bouton Device identity renomme **« Purge stale keychain »**
  (`NWL`, FR « Purger le keychain obsolete », ES « Purgar keychain
  obsoleto ») ; alerte `N item(s) removed (legacy L, ghost G)`.
- Design Blaze inchange (memes helpers `addSection`/`addRowsCard`).
